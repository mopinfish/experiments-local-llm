# ファインチューニング性能比較実験 計画書

## 1. 実験概要

### 1.1 目的
RAGシステム（Phase 6.2.1: 91.6pt）と、ファインチューニングしたLLMの性能を比較し、以下を明らかにする：

1. **RAG vs ファインチューニング**: 地理的POIクエリタスクにおいて、どちらのアプローチが有効か
2. **相補性の検証**: RAGとファインチューニングを組み合わせた場合の効果
3. **タスク別適性**: L1-L5の難易度レベルごとに、どちらのアプローチが適しているか

### 1.2 背景
現在のシステムは構造化RAG（ベクトル検索＋空間処理）により高いスコアを達成しているが、以下の疑問が残る：

- LLMに渋谷エリアのPOI知識を直接学習させた場合、推論品質は向上するか？
- RAGのコンテキスト生成オーバーヘッド（約22秒/クエリ）を削減できるか？
- Phase 7以降の複数エリア対応において、どちらのアプローチがスケーラブルか？

### 1.3 仮説

| 仮説 | 説明 |
|-----|------|
| H1 | ファインチューニングモデルはL1-L2（基礎検索・空間推論）でRAGと同等以上の性能を達成できる |
| H2 | ファインチューニングモデルはL4-L5（意思決定・高度推論）でRAGに劣る（動的コンテキスト生成が必要なため） |
| H3 | RAG + ファインチューニングの組み合わせが最高性能を達成する |
| H4 | ファインチューニングモデルは推論速度が大幅に向上する（RAGのコンテキスト生成が不要なため） |

## 2. 実験設計

### 2.1 比較対象モデル

| モデル | 説明 | 期待される特性 |
|--------|------|---------------|
| **ベースライン** | Qwen2.5-7B-Instruct（4bit量子化）+ RAGなし | 事前学習知識のみで回答 |
| **RAG** | Qwen2.5-7B-Instruct + 構造化RAG（Phase 6） | 現行システム（91.6pt） |
| **FT-Base** | Qwen2.5-7B-Instruct + QLoRAファインチューニング | POI知識を直接学習 |
| **FT+RAG** | ファインチューニングモデル + 構造化RAG | 両アプローチの統合 |

### 2.2 ファインチューニング手法

**採用手法: QLoRA（Quantized Low-Rank Adaptation）**

選定理由：
- Google Colab T4 GPU（16GB VRAM）で実行可能
- 7Bパラメータモデルを効率的にファインチューニング
- 学習時間・計算コストを抑制

**ハイパーパラメータ（初期設定）:**

```python
# QLoRA設定
lora_config = {
    "r": 16,                    # LoRAランク
    "lora_alpha": 32,           # スケーリング係数
    "lora_dropout": 0.05,       # ドロップアウト率
    "target_modules": [         # 適用対象モジュール
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj"
    ],
    "bias": "none",
    "task_type": "CAUSAL_LM"
}

# 学習設定
training_config = {
    "num_train_epochs": 3,
    "per_device_train_batch_size": 4,
    "gradient_accumulation_steps": 4,
    "learning_rate": 2e-4,
    "warmup_ratio": 0.1,
    "fp16": True,
    "optim": "paged_adamw_8bit",
    "max_seq_length": 2048
}
```

### 2.3 評価方法

既存の評価システム（evaluators_v2.py）をそのまま使用：

| レベル | 評価指標（重み付け） |
|--------|---------------------|
| L1 | keyword×0.4 + coordinate×0.3 + poi_name×0.3 |
| L2 | keyword×0.3 + coordinate×0.2 + reasoning×0.5 |
| L3 | keyword×0.2 + poi_name×0.2 + constraint×0.4 + evidence×0.2 |
| L4 | reasoning×0.3 + evidence×0.3 + constraint×0.2 + uncertainty×0.2 |
| L5 | reasoning×0.4 + evidence×0.3 + uncertainty×0.3 |

**追加評価指標:**
- **推論時間**: クエリあたりの応答時間（秒）
- **メモリ使用量**: GPU VRAMピーク使用量（GB）

## 3. 学習データセット設計

### 3.1 データ分割戦略

**重要**: テストケース（55件）は評価専用とし、学習データは別途生成する。

```
POIデータ: 1,046件
├─ 学習データ生成元: 800件（76%）
├─ 検証データ生成元: 150件（15%）
└─ テスト用（評価時参照）: 96件（9%）
    ※テストケースで言及されるPOIは学習データから除外
```

### 3.2 学習データ生成方法

POIデータから質問-回答ペアを自動生成する。テストケースと重複しないよう注意。

**生成パターン:**

#### パターン1: 単純検索（L1相当）
```json
{
  "instruction": "渋谷駅周辺の{category}を教えてください。",
  "input": "",
  "output": "{category}として、{poi_name_1}（{address_1}）、{poi_name_2}（{address_2}）...があります。"
}
```

#### パターン2: 位置情報（L1相当）
```json
{
  "instruction": "{poi_name}はどこにありますか？",
  "input": "",
  "output": "{poi_name}は渋谷駅から{direction}方向に約{distance}mの場所（緯度{lat}、経度{lon}）にあります。"
}
```

#### パターン3: 最近傍検索（L2相当）
```json
{
  "instruction": "渋谷駅に最も近い{category}はどこですか？",
  "input": "",
  "output": "渋谷駅に最も近い{category}は{poi_name}で、駅から{direction}方向に約{distance}mの距離にあります。"
}
```

#### パターン4: 比較（L2相当）
```json
{
  "instruction": "渋谷駅の東側と西側では、どちらに{category}が多いですか？",
  "input": "",
  "output": "渋谷駅の{more_side}側に{category}が多く、{more_count}件あります。一方、{less_side}側は{less_count}件です。"
}
```

#### パターン5: 集約（L2相当）
```json
{
  "instruction": "渋谷駅から{radius}m以内に{category}はいくつありますか？",
  "input": "",
  "output": "渋谷駅から{radius}m以内には{count}件の{category}があります。具体的には、{poi_list}です。"
}
```

#### パターン6: 制約付き検索（L3相当）
```json
{
  "instruction": "渋谷駅から500m以内で、{constraint}を満たす{category}を教えてください。",
  "input": "",
  "output": "条件を満たす{category}として、{poi_name}があります。{detail}"
}
```

#### パターン7: 推論・判断（L4相当）
```json
{
  "instruction": "{category}を開業するとしたら、渋谷駅周辺のどのエリアが適していますか？",
  "input": "",
  "output": "{reasoning}。したがって、{recommended_area}が適しています。{evidence}"
}
```

#### パターン8: 感度分析（L5相当）
```json
{
  "instruction": "検索範囲を300mから500mに広げると、{category}の検索結果はどう変わりますか？",
  "input": "",
  "output": "300m以内では{count_300}件、500m以内では{count_500}件となり、{diff}件増加します。{analysis}"
}
```

### 3.3 生成データ量の目標

| パターン | 生成数 | 説明 |
|---------|--------|------|
| パターン1-2 | 各200件 | 基礎的な質問応答 |
| パターン3-5 | 各150件 | 空間推論・集約 |
| パターン6 | 100件 | 制約付き検索 |
| パターン7-8 | 各50件 | 高度な推論 |
| **合計** | **約1,000件** | |

### 3.4 データ品質管理

1. **重複排除**: 同一POIに対する類似質問を制限
2. **テストリーク防止**: テストケースの質問・回答と類似するデータを除外
3. **バランス調整**: カテゴリ・難易度のバランスを調整
4. **人手検証**: 生成データの10%をサンプリングして品質確認

## 7. リスクと対策

### 7.1 技術的リスク

| リスク | 影響 | 対策 |
|--------|------|------|
| Colab GPU制限（12時間） | 学習中断 | チェックポイント保存、段階的実行 |
| VRAMオーバーフロー | 学習失敗 | バッチサイズ削減、gradient checkpointing |
| 学習データ品質不足 | 性能低下 | パターン追加、人手検証強化 |
| テストリーク | 不正確な評価 | 厳密なデータ分割、類似度チェック |

### 7.2 実験設計リスク

| リスク | 影響 | 対策 |
|--------|------|------|
| 学習データ量不足 | 過学習 | データ拡張、正則化強化 |
| ハイパーパラメータ未最適化 | 性能低下 | グリッドサーチ（時間許容内） |
| 評価指標の偏り | 不公平な比較 | 複数指標での総合評価 |

## 10. Phase 7以降への示唆

この実験結果は、以下の方針決定に活用される：

### 10.1 複数エリア対応（Phase 7）への影響

- **ファインチューニング優位の場合**: エリアごとのアダプタ作成を検討
- **RAG優位の場合**: ベクトルストアのマルチエリア対応を優先
- **相補的の場合**: 両アプローチのハイブリッド設計

### 10.2 全国展開（Phase 8）への影響

- **スケーラビリティ**: ファインチューニングは新エリア追加に再学習が必要
- **保守性**: RAGはPOIデータ更新のみで対応可能
- **コスト**: 学習コスト vs 推論コストのトレードオフ

### 10.3 MCPサーバ統合（Phase 9）への影響

- **応答速度**: ファインチューニングモデルの速度優位性はMCP統合で重要
- **柔軟性**: RAGの動的コンテキスト生成はMCP経由の外部データ連携に有利
